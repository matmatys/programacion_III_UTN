El punto de partida

Una vista, cuatro estados posibles

Cuando programamos una pantalla que muestra datos, pensamos: "muestro la lista". Pero esa vista es asincrónica: pide datos a una API, espera, y algo termina pasando. Hay al menos cuatro escenarios distintos, y solo uno es "todo salió bien".

Loading

Pedimos los datos y estamos esperando. El usuario no sabe si tarda, si la app se colgó, o si su click se registró.

Success · happy path

Los datos llegaron y los mostramos. Lo único en lo que pensamos por defecto, y por eso el resto suele quedar roto.

Empty

La respuesta llegó vacía. ¿Por qué? ¿Es la primera vez? ¿Filtró algo? ¿Hay un bug?

Error

Algo falló: red caída, servidor que devolvió 500, sesión expirada. El usuario necesita saber qué pasó.

→ Si solo manejamos el happy path, los otros tres se ven como una pantalla en blanco. Hoy los volvemos explícitos.
Frontend · estados de UI 2 / 6
Estado 1 · Loading

El usuario tiene que saber que algo está pasando

Sin feedback visual, el usuario se pregunta si la app se colgó, si su click no se registró, o si ya terminó y no pasa nada. Cualquier de esas tres dudas lo lleva a recargar, reintentar, o irse. Un buen estado de loading evita las tres.

Spinner

"Algo está pasando"

  • Indicador genérico: un círculo que gira.
  • Comunica actividad, no qué viene.
  • Bueno para acciones puntuales: enviar un form, login, guardar.
  • Tapa toda la pantalla (overlay) cuando bloquea la interacción.
Skeleton

"Esto es lo que va a aparecer"

  • Placeholder con la forma del contenido futuro (cajas grises).
  • Reduce la sensación de espera: el usuario ya entiende qué esperar.
  • Bueno para listas, cards, dashboards.
  • Mantiene el layout estable (no hay "saltos" cuando llegan los datos).
→ Detalle útil: si la operación dura menos de ~300ms, mostrar loading empeora la experiencia (flicker). Conviene esperar antes de mostrarlo.

Estado 2 · Error

Cuando algo falla, no dejes al usuario en silencio

Una pantalla en blanco frente a un error es de lo peor que puede pasar. El usuario no sabe si es él, si es la app, o qué hacer. Un buen estado de error explica qué pasó en lenguaje humano y ofrece una salida.

Qué mostrar
  • Mensaje claro, sin jerga técnica ("Algo falló cargando tus conversaciones").
  • Una acción: reintentar, recargar, volver al inicio.
  • Si tiene sentido, distinguir el tipo: red caída (offline), permisos (403), no existe (404), server (500).
  • Mantener la app navegable: el usuario debería poder irse a otra parte.
Qué no hacer
  • Mostrar el stack trace o un [object Object].
  • Dejar la pantalla en blanco o congelada.
  • Avisar con un alert() que rompe el flujo.
  • Culpar al usuario por algo que no es su problema (un 500 nunca es culpa suya).
→ Regla de oro: el usuario tiene que poder seguir usando la app aunque una parte haya fallado. Un error no es el fin del mundo, es una parte del mundo.

Estado 3 · Vacío

"Vacío" no significa lo mismo en todos los casos

Es el estado más olvidado. "No hay datos" parece autoexplicativo, pero hay tres razones distintas para estar vacío, y cada una pide un mensaje y una acción distintos. Confundirlas hace que el usuario piense que la app está rota.

1 · Vacío inicial

El usuario nunca creó datos. Es la primera vez.

Oportunidad de onboarding:

"Todavía no tenés conversaciones. Empezá la primera." + botón.

2 · Vacío por filtro

El usuario tiene datos, pero el filtro/búsqueda actual no devuelve nada.

La acción es relajar el filtro:

"Ninguna conversación coincide con 'foo'." + opción de limpiar.

3 · Vacío por eliminación

Tenía datos, los borró a todos. Es un estado momentáneo.

La acción es deshacer o crear:

"Vaciaste todo. ¿Querés crear una nueva?"

→ El vacío es la mejor oportunidad para guiar al usuario: es exactamente cuando no sabe qué hacer.

Para cerrar · práctica

Lo aplicamos al chat

Vamos a tomar la lista de conversaciones del chat y le vamos a agregar el manejo explícito de los tres estados. Hoy esa vista solo muestra el happy path: si carga, no se nota; si falla, queda en blanco; si está vacía, no dice nada. Vamos a arreglarlo.

// patron: cada estado con su *ngIf
<app-skeleton-list *ngIf="loading"></app-skeleton-list>

<app-error-state
  *ngIf="!loading && error"
  [error]="error"
  (retry)="reload()"
></app-error-state>

<app-empty-state *ngIf="!loading && !error && !conversations.length">
  Todavía no tenés conversaciones.
  <button (click)="crear()">Crear la primera</button>
</app-empty-state>

<app-conversation-list
  *ngIf="!loading && !error && conversations.length"
  [items]="conversations"
></app-conversation-list>

Lo que vamos a hacer

  • Modelar los tres estados con flags privados en el service.
  • Manejarlos en el template con *ngIf y <ng-container> anidados.
  • Crear componentes reutilizables: skeleton-list, error-state, empty-state.
  • Probarlo cortando la API a propósito (DevTools → offline) para ver cada estado.
→ Después de hoy, ninguna vista nuestra vuelve a tener una pantalla blanca esperando que el usuario adivine qué pasó.
